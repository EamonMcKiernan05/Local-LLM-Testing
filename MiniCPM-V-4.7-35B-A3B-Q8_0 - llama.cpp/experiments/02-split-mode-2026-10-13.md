# 02 — Split mode on the V100s: tensor vs layer (2026-10-13)

Asked: "does tensor split not work on the v100 rig? test again with tensor split."

## What we found before running anything

- **`-sm row` — the classic CUDA row split — no longer exists upstream.** `74976e1ae
  "CUDA: remove -sm row, refactor cuBLAS"` took it out; on b11580 the CUDA backend exports no
  split-buffer type at all (only SYCL/Hexagon do), so the loader dies in one second with
  `device CUDA0 does not support split buffers`. This is not a V100 limitation — it is the
  current state of CUDA in mainline llama.cpp. (The 3060-era sweeps in this repo used row split
  on an older build, b10068/b11041 era — that path is gone.)
- **The working tensor-split mode is `-sm tensor`** (flag list in b11580: `none, layer, row,
  tensor`; help text: "tensor: split weights and KV across GPUs (parallelized, EXPERIMENTAL)").
  It is guarded by `llm_arch_supports_sm_tensor()` in `src/llama-arch.cpp` — a blocklist that
  returns true by default; `qwen35moe` is not on it, so the mode is allowed. Upstream has been
  actively stabilising it (e.g. "TP: fix split state and granularity for fused QKV gemma4,
  qwen35 (#28965)").
- **No MTP arm to pair it with**: the official GGUF has no nextn/MTP tensors (733-tensor file
  checked) and the source checkpoint's safetensors index has 0 of 1,152 MTP keys. Nothing to
  test there.

## Setup

Second six-depth bench, same model file, same build, same prompts, same session parameters as
the layer-split run — only the split flags differ:

```
--split-mode tensor --tensor-split 1,1     (env GGML_CUDA_ALLREDUCE=internal, as always)
```

Load 10m31s from HDD (layer split: 8m52s). VRAM at 250K: 21.6 + 20.5 GB (layer: 22.8 + 20.5).
Server healthy, generation clean, zero errors in the log.

## Results

| depth | layer: prefill / decode | tensor: prefill / decode | decode Δ | prefill Δ |
|---|---:|---:|---:|---:|
| 20K | 754.0 / 87.5 | 406.7 / 92.5 | +5.7% | −46.1% |
| 60K | 670.5 / 79.7 | 431.4 / 87.4 | +9.7% | −35.7% |
| 100K | 618.4 / 73.7 | 420.7 / 83.2 | +12.9% | −32.0% |
| 150K | 538.2 / 66.8 | 401.4 / 78.9 | +18.1% | −25.4% |
| 200K | 476.6 / 61.1 | 378.0 / 74.6 | +22.1% | −20.7% |
| 250K | 431.4 / 57.3 | 356.5 / 70.3 | +22.7% | −17.4% |
| **mean** | | | **+15.2%** | **−29.5%** |

## What the numbers say

- **Tensor split trades prefill for decode, and the trade improves with depth.** Prefill cost
  falls from −46% to −17% across the range; decode gain rises from +5.7% to +22.7%. Mechanism:
  tensor mode halves every weight read per card and needs one cross-card reduction per layer —
  at shallow depths that reduction (PCIe 3.0, no NVLink) dominates a short prefill, while at
  depth the prefill per-layer work is large enough to amortise it. Decode is a per-token
  latency game, and splitting each token's matmuls across both cards' SMs wins there at every
  depth measured.
- **Tensor-split prefill is nearly flat with depth** (407 → 356, −12% across the range) where
  layer split falls 754 → 431 (−43%). Different bottleneck, different curve shape.
- **Posture per workload**: token-generation-heavy serving at deep context favours tensor
  (e.g. +23% decode at 250K for −17% prefill); prompt-processing-heavy use at shallow context
  strongly favours layer. The two cards on this box see both.

## Standing change

Per Eamon (2026-10-13, mid-run): **tensor split is the default for llama.cpp testing on this
rig going forward; layer split is a fallback only when tensor genuinely does not work**
(arch blocklist, load failure). Noted in the `llama-cpp-serving-sweep` skill.
