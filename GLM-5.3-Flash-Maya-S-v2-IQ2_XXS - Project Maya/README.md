# GLM-5.3-Flash (Maya-S) on Project Maya — the bench record on box .5

**66 recorded runs on GLM-5.3-Flash (321B MoE, ~18B active) served by Project Maya on 2× Tesla
V100 32 GB — measured 2026-10-07 to 2026-10-15 on the box brought up 2026-09-30.** One GGUF set
throughout: Maya-S-v2 IQ2_XXS (47.8 + 47.8 + 0.8 GB), layer-split across both cards. Every number
came off a real run on this hardware; nothing is estimated from a datasheet.

The findings that matter:

- **The v1.1.11 engine update lifts decode ~7 % on a three-run-per-side pair (mean +6.7 %, every
  depth positive: +9.1 / +6.8 / +4.3 %), and more at short prompts — +9 to +16 % across 0.5K–10K
  (mean +12.5 %; decode peaks ~21.3 tok/s at 1K).** Prefill reads equal-to-−4 % (a small consistent
  dip at short prompts is shown in experiment 05, not smoothed over). The update also migrates the
  config itself: the shipped expert profile is added at its first start.
- **The v1.0.34 engine update lifts prefill 77–113 % on a same-day, same-config pair (mean +97.5 %)** —
  260 → 526 tok/s at 40K prompt depth, 269 → 476 at 60K — **and decode rises across all three
  depths (mean +46.4 %)**. The v1.0.33 pair measured 40 minutes earlier was superseded by the next
  release before publication (experiments 03/04).
- **The v1.0.9 engine update adds 40–90 % prefill** on a same-day, same-config pair: 161.7 → 226.4
  tok/s at 20K prompt depth, 142.3 → 270.8 at 60K (mean **+69.1 %**; decode within noise at +0.9 %).
  The update's prefill work (SSD read-ahead + tensor-core attention) is the whole story of the gain.
- **The previous build re-runs within ~1 % of its archived numbers** — prefill +0.8 % mean over the
  three depths, decode −0.1 % mean with cell swings inside the ±5–10 % single-rep band — so the
  same-day pair is clean (experiment 02).
- **Decode sits at ~13–16 tok/s, prefill reaches 271 tok/s** on the tuned 64K config; the per-depth
  numbers are on the cards.
- **The boot NVMe caps decode**: ~600 of the 12,096 experts re-stream off the DRAM-less SK hynix
  BC501 every token, and measured disk waits are about half the per-token cost (experiment 01).
- Runs recorded: **66 — all 66 measured, 0 failed** (warm-ups were discarded by design; the
  2026-10-15 calibration battery — 3 of the 66 — is excluded from the pair by design).

## Method, and what is deliberately not claimed

- **Three runs per side on the 2026-10-15 pair** (alternated loads, one load per battery, means; a
  discarded post-copy calibration battery; the audit and spreads are in experiment 05), plus six more
  batteries for the 0.5K–10K short-prompt extension. Earlier
  pairs are one run per arm.
- **One measured run per arm, unique documents, a discarded warm-up.** The bench slices the same
  three corpus documents per fixed depth (Frankenstein / Sherlock / a second Sherlock cut) with the
  pack tokenizer, exact-token; every request carries a unique tag so the prefix cache cannot flatter
  a run. Per-cell run-to-run noise: **≤ ~1.5 % on prefill, −4…+10 % on decode** — measured on the
  one repeated configuration this dataset has (the previous-build re-run vs its archive).
- **The v1.0.9 comparison is a same-day pair** as the house method requires: the previous build was
  rebuilt from its commit (`142540b`) and re-run the same morning as the update, same config as
  served (64K context, RAM headroom 3) — only the engine differs.
- **The v1.0.33 comparison is another same-day pair**: v1.0.9 (`7655730`) was rebuilt and re-run
  the same morning, same config as served — only the engine differs. Its agreement check (re-run
  vs the 2026-10-08 archive) is in experiment 03: prefill −2.1 % mean; decode sat ~6 % under its
  archive, so the pair's decode mean carries that caveat.
- **The v1.0.34 comparison repeats the exercise the same afternoon** (the release landed 40 minutes
  after experiment 03's measurements): v1.0.9 rebuilt and re-run again — prefill agreement −1.5 %
  mean, decode ~10 % under its archive (experiment 04).
- **Decode claims are kept to the band, not to cells.** The three decode deltas of the pair
  (+13.4 / −7.4 / −3.4 %) are one run each; the mean (+0.9 %) is the claim.
- **Every derived number is the per-depth delta** — `100 × (after / before − 1)` on the unrounded
  values — and appears in `data/csv/release-deltas-*.csv` before it appears on a chart.
- **Not claimed:** that the gains generalise beyond these depths — 20K–60K is all the 64K config
  can take; and nothing about other quants (Maya-M was never benchmarked here).

## Reproducing

The config both sides ran on is `data/raw/config-64k-served.json` (on the box:
`~/project-maya/maya-maya-s-v2-iq2_xxs.json`). A measurement is one HTTP call through the
model-bench harness on box .5:

```bash
cd ~/model-bench
export MODEL_BENCH_GGUF="/mnt/models/Maya-data/models/glm-5.3-flash-maya-s-v2-iq2_xxs/GLM-5.3-Flash-Maya-S-v2-IQ2_XXS-00001-of-00003.gguf"
export MODEL_BENCH_PACK="/mnt/models/Maya-data/models/glm-5.3-flash-maya-s-v2-iq2_xxs/pack/tokenizer"
/home/eamon/Strata/.venv/bin/python bench.py --url http://127.0.0.1:8080 \
  --label <label> --depths 20k,40k,60k
```

Give every request a unique first line (an identical prompt is a cache hit, not a measurement),
and discard the first request after any load.

## What we still cannot answer

- **One run per arm on the pre-v1.1.11 pairs** — the ±noise band is estimated from the few repeats
  this dataset holds (the previous-build re-run, the 2026-10-12 v1.1.1 runs, and experiment 05's
  three runs per side).
- **The 2026-10-15 pair is three cells per side** — enough to state the decode mean; single cells at
  these depths still wander (experiment 05 lists the ranges).
- **The drive cap is characterised, not fixed** — a proper NVMe is the expected fix (~29 tok/s-class
  decode by arithmetic), never verified here; one is on order but not yet delivered.
